A twelve-week practice path

Reading about this field has sharply diminishing returns. This is the build order that turns the previous lessons into something you can actually do.

#How to use this

Every block ends with something that runs on your own machine. The weeks are a suggestion; the ordering is not, because each one depends on the last.

#Weeks 1–2 · SQL, properly

Not SELECT ... WHERE. The things that data engineering actually runs on: window functions, CTEs, self-joins, GROUP BY with HAVING, date arithmetic, and reading a query plan.

Window functions especially. Deduplication, sessionisation, running totals, and slowly changing dimensions are all written with them, and every one of those appears in the lessons above.

Project

Load a public dataset over 1 GB — NYC taxi trips is the classic — into DuckDB on your laptop and answer ten non-trivial questions with SQL.

DuckDB is the fastest way to experience columnar analytics with no cloud account, no cluster, and no setup. Install it and you are running an OLAP engine in about thirty seconds.

#Weeks 3–4 · Python for moving data

Requests and pagination, retries with exponential backoff, reading and writing Parquet with pyarrow or polars, handling secrets, and structured logging.

Project

Write an extractor for a free public API that lands raw JSON to disk, partitioned by date, then converts it to Parquet.

Then make it safe to rerun — same input, same output, no duplicates — and prove it by running it three times and comparing row counts. That proof is the point of the exercise. It is Reliability made concrete.

#Weeks 5–6 · Storage, formats and modelling

Re-read Storage and Modelling, then measure the claims yourself. Compare file sizes and query times for the same data as CSV against Parquet, partitioned against not. Watching a 30-second query become 0.4 seconds on your own machine teaches this better than any explanation.

Project

Model your dataset into a star schema. Write the grain of your fact table in a comment — "one row per…" — before writing any SQL. Then implement one SCD Type 2 dimension with valid_from, valid_to and a surrogate key.

#Weeks 7–8 · The transformation layer

Learn dbt, or SQLMesh. Sources, models, ref(), materialisations, tests and documentation. Build a raw → staging → marts project with real layering.

Project

Convert weeks 5–6's SQL into a dbt project with at least a uniqueness test, a not-null test, a relationship test, and one incremental model.

Then break something upstream on purpose — rename a column, duplicate a key, null out a field — and watch which test catches it and which does not. The tests that fail to fire are the interesting result.

#Weeks 9–10 · Orchestration

Airflow, Dagster or Prefect. Focus on DAG structure, the logical-date parameter, retries, sensors and backfills rather than on the tool's configuration surface.

Project — the one that teaches the most

Schedule your pipeline to run daily. Let it run for several days. Then delete a week of output and backfill it.

If the result afterwards is byte-identical to before, your pipeline is idempotent and correctly parameterised. If you get duplicates, or seven copies of today's data, you have just reproduced the single most common production bug in data engineering — on your laptop, where it costs nothing.

#Weeks 11–12 · Scale and streaming

Spark fundamentals — partitions, shuffle, skew, spill — enough to read a job and reason about why it is slow. Then Kafka basics: producing, consuming, offsets, partitions.

Project

Run Kafka locally. Produce synthetic events, consume them into partitioned Parquet, and compute a windowed aggregate.

Then kill the consumer mid-run and restart it. Count the rows before and after. Whatever you observe — duplicates, gaps, or neither — is Reliability happening to you in person, and it will stay learned.

#After the twelve weeks

  • Read Designing Data-Intensive Applications properly, a chapter a week. It will be much easier now that you have built something, and much more useful than it would have been at week one.
  • Retrofit the hard parts. Take a pipeline you already built and add the things from Quality and Cost: freshness monitoring, the six test categories, a runbook, a cost measurement.
  • Practise the framework out loud. How would you design analytics for a music streaming service? A food delivery app? A hospital? Say the answer aloud using the eight steps. Fluency in the framework is a separate skill from knowing the content, and it only comes from rehearsal.
A note on portfolios

A small pipeline that is idempotent, tested, monitored, documented, and honest about its trade-offs is worth more than an elaborate one that only works when nothing goes wrong.

Interviewers can tell the difference within about two minutes, and the second kind is much more common — which means the first kind stands out more than its size would suggest. A README that says "here is what this does, here is what breaks it, here is what I would do differently at ten times the volume" is a stronger artefact than another five services.

#Checklist

  • Have a running query engine on your own machine and a dataset over a gigabyte in it
  • Have written an extractor you have proven is safe to rerun
  • Have measured the CSV-to-Parquet difference yourself rather than taking this course's word for it
  • Have watched a data test catch a bug you introduced deliberately
  • Have performed a backfill and verified the output was unchanged
  • Have killed a streaming consumer mid-run and looked at what happened to the data
