The hard parts

Quality, contracts and observability

Broken pipelines page you. Wrong data does not — which is exactly what makes it the more dangerous failure, and the one worth building defences against.

#The failure that does not announce itself

Imagine a pipeline that has run successfully every morning for five weeks. Green ticks the whole way down. It has also, for those five weeks, been undercounting revenue by 4% because an upstream team added a new order status your CASE statement does not handle.

Nobody knows. Decisions have been made on those numbers. When it is finally discovered, the cost is not the bug — it is the five weeks, and the fact that for the next year people will ask "are we sure this number is right?" before every meeting.

That is the failure this lesson defends against. It is a different problem from uptime, and it needs different tools.

#Schema changes: which ones are safe

Schemas change. The question is whether a given change is compatible with readers that already exist.

ChangeSafe?Why
Add a nullable columnSafeExisting readers ignore it
Add a required columnBreakingOld rows have no value for it
Drop a columnBreakingDownstream queries referencing it fail
Rename a columnBreakingIt is a drop and an add wearing a disguise
Widen a type (int → bigint)Usually safeEvery old value still fits
Narrow a type (bigint → int)BreakingSilent overflow or truncation
Change the meaning, not the typeWorst of allamount switches from dollars to cents. Nothing errors. Every number is wrong by 100×
Why the last row is the worst

Every other change in that table produces an error somewhere, and an error is a gift — it tells you immediately, in a log, with a line number.

A semantic change produces no error at all. The pipeline runs, the types match, the tests pass, and the numbers are wrong. This is why schema validation alone is insufficient and why the distribution tests below matter: they are the only mechanism that catches a value which is well-formed and meaningless.

#Defences, from cheap to serious

  • Never SELECT * into a persisted model. Pin the columns you depend on, so a new upstream column cannot surprise you and a dropped one fails loudly at build time.
  • Land raw permissively, enforce at the first transformation. If raw is JSON, an unexpected field cannot break ingestion. Apply the schema one step later, where failing is safe.
  • Use a schema registry (common with Avro on Kafka) to reject incompatible producer changes at publish time — before the bad data exists.
  • Write a data contract. See below.

#Data contracts

A data contract is an agreement between the team producing data and the teams consuming it, covering schema, semantics, freshness, and how changes are made.

It sounds bureaucratic. In practice the lightweight version is a schema file living in the producer's repository plus a CI check that fails their build if they break it — and that single arrangement prevents most cross-team data incidents, because it moves the failure from your 3 a.m. pager to their pull request.

Analogy

An API has a version, documentation, a deprecation policy, and a test suite that fails when someone breaks it. Nobody would ship a public API by letting any developer rename a field whenever they liked.

A data contract is that same discipline applied to a table or a topic. The reason data usually lacks it is historical, not principled: analytics started as people reading each other's databases, and the habit stuck.

Where it breaks: an API has one obvious owner and a visible caller list. A table often has neither, which is why contracts need lineage to be enforceable — you must be able to see who would break.

#The six test categories

Treat these as a checklist to apply to every table that matters. Most real data incidents are caught by one of these six, and teams that write tests ad hoc reliably miss two or three of them.

#TestAsksCatches
1FreshnessIs max(updated_at) within the SLA?A source that silently stopped delivering
2VolumeIs today's row count in the expected range?Partial loads, double loads, a filter that went wrong
3UniquenessIs the primary key actually unique?Broken joins, duplicate writes, fan-out
4Not-nullAre required fields populated?Upstream schema drift, failed lookups
5ReferentialDo all foreign keys resolve?Late-arriving dimensions, orphaned facts
6DistributionIs revenue ≥ 0? Is status='unknown' under 1%?Semantic changes — the ones nothing else catches
Uniqueness deserves special attention

A duplicate in a dimension table does not produce an error. It produces a join that returns two rows where it should return one — so every measure joined through it silently doubles.

This is the most common cause of "the dashboard says we made twice as much as we did", and a single uniqueness test on the dimension's key would have caught it at build time. If you only ever write one test per table, write this one.

#Where tests belong, and what failure should do

Each test also needs a decision about severity:

  • Blocking — the pipeline stops and nothing downstream is published. Correct for correctness-critical tables, where wrong data is worse than late data. This is sometimes called a circuit breaker.
  • Warning — the pipeline continues, someone is notified. Correct for noisy heuristics and soft thresholds.
Do not make everything blocking

The instinct is to block on every test, since wrong data is bad. The result is a pipeline that halts three times a week on soft thresholds, an alert channel everyone mutes, and eventually a real failure that nobody looks at.

An ignored alert is worse than no alert, because it creates the appearance of monitoring without the substance. Block on the small number of tests where publishing wrong data is genuinely worse than publishing nothing.

#Observability

You should find out a pipeline is broken from your monitoring, not from an executive's email. Four things to build:

1

#Freshness SLAs

Publish, per important table, when it will be updated by. "Orders mart is fresh as of 06:00 daily" is a contract — monitor it and alert on breach.

2

#Lineage

A graph of which tables feed which. Answers "what breaks if I change this?" and "where did this bad number come from?" Modern transformation tools generate it from your code.

3

#Run metadata

Log durations, rows in, rows out, and cost per run — then trend them. A job whose runtime has quietly tripled over a month is a future 3 a.m. incident announcing itself early.

4

#Runbooks

For each critical pipeline: how to rerun it, what is safe to backfill, who owns the source, who to tell. Written before you need it, because you will need it at the worst possible moment.

#A useful habit: reconciliation

The strongest test you can write compares your number to an independently produced number for the same thing.

If Stripe says you processed $482,110 yesterday and your warehouse says $479,884, something is wrong, and you know it within a day rather than at quarter-end. Reconciliation tests catch entire categories of error that no schema check or null test could — missing rows, double-counted joins, currency mistakes, silently dropped partitions — because they check the meaning rather than the shape.

Wherever a source system publishes its own totals, compare against them.

#Checklist

  • Classify a proposed schema change as safe or breaking, and explain why a semantic change is more dangerous than a dropped column
  • Describe the lightweight version of a data contract and where it lives
  • Name all six test categories from memory and say what each one catches
  • Explain why a duplicate in a dimension table doubles your revenue figures
  • Decide whether a given test should block or warn, and argue against blocking on everything
  • Design a reconciliation test for a pipeline you have built
