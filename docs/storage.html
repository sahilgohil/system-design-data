The building blocks

Storage, formats and layout

Where the data sits, what format it sits in, and how it is arranged. These three choices affect cost and speed more than almost anything else you will decide.

#The shift that made everything else possible

For decades, a database meant one thing: a machine with disks attached, where storage and the engine that read it were welded together. Needing more query power meant buying a bigger machine — and paying for its disks whether you used them or not. Storing five years of history meant paying for compute you were not running.

Then cloud object storage arrived — Amazon S3, Google Cloud Storage, Azure Data Lake Storage — and broke the weld. Storage became a separate, absurdly cheap service, and compute became something you spin up, use, and switch off.

This separation of storage and compute is the defining architectural change of the last fifteen years, and it is why you can now keep 500 TB of history and pay almost nothing until someone asks a question of it.

What object storage actually is

A giant key–value store where the keys look like file paths and the values are files. That is all. It is cheap (roughly $20–25 per TB per month), extraordinarily durable, and has no compute of its own.

The trade-off: tens of milliseconds of latency per request, no transactions, no indexes. Everything in the rest of this page is, in one way or another, about adding those things back.

#What a "lakehouse" is, without the marketing

You will hear the word constantly. Here is what it means mechanically.

A folder of Parquet files in S3 is not a table. You cannot update a row, two writers will corrupt each other, and there is no way to ask what the data looked like last Tuesday. A table format — Iceberg, Delta Lake, Hudi — adds a metadata layer that tracks which files belong to the table at which point in time. That single addition buys you transactions, UPDATE and DELETE, schema evolution, time travel, and safe concurrent writers.

What to actually choose as a beginner

If your data is under roughly 10 TB and your team writes SQL, use a cloud warehouse. Full stop.

The lakehouse path earns its complexity at large scale, with several processing engines, or when avoiding vendor lock-in is a real business requirement rather than a preference. Complexity has a running cost, and beginners consistently underestimate it.

#Three mechanisms that make Parquet fast

Worth knowing by name, because you will see all three in query plans and documentation:

  • Column pruning — the reader fetches only the columns your query mentions. Selecting 3 columns from a 200-column table reads 1.5% of the file.
  • Predicate pushdown — every file stores min/max statistics per column per row-group, so a filter like WHERE order_date = '2026-03-01' can skip entire files without decompressing them.
  • Encoding and compression — dictionary and run-length encoding on same-type columns, then Snappy or ZSTD on top.

The practical effect: a 10 GB CSV routinely becomes a 1–1.5 GB Parquet file, and queries against it run five to fifty times faster. Converting a raw CSV or JSON landing zone to Parquet is often the single highest-return change a beginner can make to an existing pipeline.

The small file problem

A streaming job that writes a file every 30 seconds produces 2,880 files a day and about a million a year. Every query must then open a million files, and the per-file overhead — list, open, read the footer — completely dominates the actual reading. Queries crawl; metadata operations start timing out.

Target 128 MB to 1 GB per file. Below about 32 MB you are heading for trouble at scale. The fix is compaction: a scheduled job that rewrites many small files into fewer large ones. Table formats provide it as a built-in operation; on raw Parquet you must write and schedule it yourself. Budget for it as ongoing operational work, not a one-off.

#Layout: how you arrange files decides what a query costs

In most cloud data platforms you are billed, directly or indirectly, for data scanned. So the cheapest query is the one that reads the least, and layout is how you make that happen.

#Partitioning

Partitioning splits a table into physical subdirectories by the value of a column, almost always a date:

s3://lake/orders/dt=2026-03-01/part-0001.parquet
s3://lake/orders/dt=2026-03-02/part-0001.parquet

A query filtered to March reads two directories instead of the whole table. That skipping is called partition pruning, and it is the workhorse optimisation of the entire field.

Choosing a partition key well:

  • Partition on what you filter by, which is a date in the overwhelming majority of cases.
  • Aim for 100 MB – 1 GB per partition. This is the same size logic as file sizing, one level up.
  • Never partition on a high-cardinality column. Partitioning by user_id across 10 million users creates 10 million tiny directories and will destroy performance rather than improve it.
  • Do not over-partition by time. Hourly partitions on a table with 10 MB a day gives you 8,760 near-empty directories a year. Daily would be better; monthly might be better still.
Partitioning versus clustering

These get conflated constantly, and the distinction is simple once stated.

Partitioning is physical separation into directories. It works for low-cardinality columns you filter on — dates, regions, event types.

Clustering (also called sorting, or Z-ordering) physically orders rows within files so that min/max statistics become selective and files can be skipped. It is what you use for high-cardinality filter columns where partitioning would be a disaster — user_id, product_sku.

One-line test: if the number of distinct values is in the thousands or more, you want clustering, not partitioning.

#Retention

Nobody ever remembers to delete data, and storage bills grow forever. Decide at design time when partitions expire or move to cold storage. It is far easier to write the policy on day one than to negotiate it after someone notices the bill.

#The one rule about raw data

Land what the source actually said, unmodified, and never edit it.

This feels wasteful and is not. When you discover a parsing bug six months from now — and you will — the raw copy is the difference between reprocessing history in an afternoon and telling everyone the last six months of that metric are simply lost. It is also your only defence when someone claims the source system said something different from what you reported.

Try this

Take any CSV over a gigabyte. Load it into DuckDB, run an aggregation, and time it. Then COPY it to Parquet, run the identical query, and time that. Compare the file sizes too.

Watching a 30-second query become a 0.4-second query on your own machine teaches this page better than any explanation can.

#Checklist

  • Explain what separating storage from compute changed, and why it made keeping five years of history reasonable
  • Say what a table format adds to a folder of Parquet files, and name three things it enables
  • Choose between a warehouse and a lakehouse for a given team, and defend it on complexity rather than capability
  • Name the three mechanisms that make Parquet fast, and explain predicate pushdown to someone who has never heard of it
  • Diagnose the small file problem from a symptom, and say what fixes it
  • Pick a partition key for a table given its query patterns — and say when to cluster instead
