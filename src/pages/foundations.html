The problem this whole field exists to solve

A company has an application. The application has a database, and that database is very good at one thing: answering questions about one customer, one order, one session, right now.

Then someone asks: what did revenue do by region over the last three years, split by product category?

You can write that query against the application's database. It will work — for a while. Then the company grows, the query starts taking four minutes, and one Tuesday it locks a table during a sale and the checkout page goes down. Now you have learned the founding lesson of data engineering the expensive way: the database that runs your business is the wrong place to analyse your business.

So you copy the data somewhere else. And immediately you have a dozen new problems. How often do you copy it? What happens when the copy fails halfway? What if a row was deleted in the source? What if someone renames a column? Who notices when the numbers go wrong?

Answering those questions well, at scale, for years, is data system design.

A definition worth memorising

Data system design is deciding how data moves from where it is produced to where it is useful — reliably, correctly, affordably, and in a way the next engineer can maintain.

How this differs from the system design you may have read about

If you have read about system design before, it was probably backend system design: design Twitter, design a URL shortener. That discipline optimises for many users doing tiny operations at once. Data system design optimises for few consumers doing enormous operations, usually not in real time. The questions are genuinely different.

Backend system design asksData system design asks
How do I serve 50,000 requests per second?How do I process 500 GB a day without going bankrupt?
How do I keep p99 latency under 100 ms?How fresh must this table be — 5 minutes or 6 hours?
How do I avoid downtime?How do I recover when yesterday's data was wrong?
How do I shard this database?How do I lay files out so a query scans 1% of them instead of 100%?

Notice the third row especially. In backend engineering, the failure you fear is the system being down — loud, obvious, everyone knows within a minute. In data engineering, the failure you fear is the system being wrong — silent, and capable of running for weeks while people make decisions on it.

The reference pipeline

Nearly every data system — a startup's first pipeline, a bank's platform, the thing your company already has — is a variation of the same five-stage shape. Learn it now, and for the rest of your career you can place any new tool or architecture by asking: which box does this fill?

Wrapped around all five stages are three concerns that apply everywhere and belong to no single box:

  • Orchestration — what runs, in what order, when, and what happens when it fails.
  • Observability — is it fresh, is it correct, what broke, what does it cost.
  • Governance — who can see what, where the personal data is, how long it is kept.

These three are the difference between a demo and a production system, and they are where most of the later pages in this course live.

OLTP and OLAP: the split that explains everything

This is the single most important idea in the course. Two kinds of database exist, built on opposite assumptions, and confusing them is the root cause of an enormous share of beginner mistakes.

OLTP (Online Transaction Processing) is the database behind your application. OLAP (Online Analytical Processing) is the database behind your analytics.

Why the storage layout is the whole story

Picture a table with 200 columns and one billion rows, and think about how the bytes sit on disk.

Row storage keeps each record's fields next to each other: all of row 1, then all of row 2. Fetching one complete record is a single seek — perfect for "show me order #4521". But summing one column means reading all 200 columns of all one billion rows, because the values you want are scattered thinly across the whole file.

Column storage keeps each column's values next to each other: every country, then every amount. Summing one column now reads one two-hundredth of the data. And because a column holds values of a single type — often with few distinct values, like country — it compresses five to twenty times better than mixed row data.

Analogy

A row store is a filing cabinet of paper forms: one folder per customer, every field about that customer inside it. Pulling one customer's file is instant. Answering "what is the average age of all customers" means opening every folder in the building.

A column store is that same data typed into one long list of every name and a separate long list of every age. The average age is one list, read once. But reconstructing a single customer's full record now means visiting two hundred different lists.

Where it breaks: a real column store does not visit those lists one at a time — it reads them in parallel, and a good one skips entire files using stored statistics. The analogy gets the trade-off right and the mechanics wrong.

This is why a query that takes 40 minutes on Postgres takes 4 seconds on an analytics warehouse. It is not that the warehouse has faster disks. It is that it reads a hundredth of the bytes.

The confusion to head off

"OLAP" sounds like it should mean slow, offline, yesterday's data, and "OLTP" sounds like it should mean live and modern. Neither is true — both have "online" in the name and both serve interactive queries.

The one-line test: OLTP is optimised for how fast one small request finishes; OLAP is optimised for how much data one big request can chew through. Freshness is a completely separate axis, and you choose it independently.

Batch and streaming are a spectrum, not a switch

The other axis you choose on is freshness: how old the data is when someone uses it. Beginners tend to treat this as a binary — batch or real-time — but it is a dial, and every notch to the right costs more money and much more engineering time.

The difference is not only cost. Batch work is bounded: you process yesterday's data, yesterday is over, so if the job fails you run it again and you are done. Streaming work is unbounded: there is no natural end, the job holds state between events, time and correctness become entangled, and "just run it again" stops being a sentence that means anything simple.

The question to ask instead

When someone asks for real-time, do not ask how fresh they want the data. Ask: what decision do you make with this, and how quickly do you make it?

A monthly board report needs daily data. A marketing dashboard needs hourly. Blocking a fraudulent transaction needs milliseconds — and should not go through your warehouse at all. In practice, "the executive wants real-time" usually means "yesterday's number feels stale", which hourly solves at a fraction of the cost.

The default is batch. Make streaming justify itself with a named decision that genuinely cannot wait.

The four constraints you are always trading between

No design maximises all four of these. Every choice in the rest of this course is a trade among them, and being able to name which one you traded away is most of what separates a considered design from a lucky one.

1

Correctness

The numbers are right, and stay right when jobs fail, data arrives late, or someone reruns last month by accident.

2

Freshness

How old the data is when it is used. The most expensive constraint to tighten, and the one most often over-specified.

3

Cost

Compute, storage, and engineer hours. The third is usually the largest and never appears on the cloud bill.

4

Maintainability

Can someone else understand, change and debug this in a year? Including you, having forgotten all of it.

A note on tools

This course names real tools — Snowflake, Kafka, Airflow, Spark, dbt — so you recognise them in job descriptions and conversations. But tools turn over every few years and the ideas do not. Column storage was a good idea in 2005 and will be a good idea in 2035; the product implementing it will have changed names twice by then.

When you meet a tool you have never heard of, ask two questions: which box of the reference pipeline does it fill, and which of the four constraints is it trading? That will get you further than reading its marketing page.

Checklist

Before moving on, you should be able to:

  • Draw the five-stage reference pipeline from memory, and name the three cross-cutting concerns
  • Explain why column storage makes an analytical query faster, in terms of bytes read — not just assert that it does
  • Give the one-line test separating OLTP from OLAP without using the words "online" or "analytical"
  • Explain to a colleague why their request for real-time data might be better served by hourly batch, and say what question you would ask them first
  • Name the four constraints, and identify which one a design has sacrificed when you are shown one
