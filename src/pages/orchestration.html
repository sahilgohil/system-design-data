Why cron is not enough

The obvious way to run a pipeline daily is a cron entry. It works for exactly one script. Then you add a second that must run after the first, so you schedule it half an hour later and hope. Then the first job occasionally takes 45 minutes, and now the second one reads yesterday's data without complaining. Nobody notices for a week.

That gap — between "it ran" and "it ran after the thing it depends on succeeded" — is the reason orchestrators exist.

The DAG

Work is modelled as a directed acyclic graph: tasks with declared dependencies, arrows one way, no loops. The orchestrator works out what can run in parallel, what must wait, and what to skip when something upstream fails.

The common tools are Airflow (the incumbent, and the one most job listings name), with Dagster and Prefect as more modern, Python- and asset-first alternatives. Warehouse-native schedulers cover simpler cases.

What an orchestrator gives you beyond a timer:

CapabilityWhat it prevents
Dependency managementA task reading data its upstream has not written yet
Retries with backoffA one-second network blip becoming a failed day
Sensors and triggersGuessing at a schedule when you could wait for the file to actually land

The two rules that matter more than the tool

You can learn any orchestrator's syntax in a week. These two properties are what actually determine whether your pipeline is safe, and they hold regardless of which tool you pick.

Rule 1 — Every task must be idempotent

Running a task twice for the same logical period must produce the same result as running it once. This is what makes retries and backfills safe, and it is the property beginners most often violate without realising.

-- NOT idempotent: the retry doubles every row
INSERT INTO daily_sales
SELECT ... FROM orders WHERE dt = '2026-03-01';

-- Idempotent: the retry replaces the same partition
DELETE FROM daily_sales WHERE dt = '2026-03-01';
INSERT INTO daily_sales
SELECT ... FROM orders WHERE dt = '2026-03-01';

-- Idempotent and atomic: MERGE on a stable business key
MERGE INTO daily_sales t
USING staged s ON t.dt = s.dt AND t.sku = s.sku
WHEN MATCHED THEN UPDATE SET ...
WHEN NOT MATCHED THEN INSERT ...;

The full treatment — including what to do when there is no stable key — is in Reliability. For now, hold onto the test: if this task ran twice by accident, would anyone be able to tell?

Rule 2 — Parameterise by logical date, never by "now"

A task should receive the period it is processing as a parameter, and must never call CURRENT_DATE or now() to work out what to do.

What happens when you break this rule

It is June. You need to rebuild March because a bug has been found. You trigger the March 1st run.

The task calls CURRENT_DATE, gets June 14th, reads June's data, and writes it into March's partition. Your history is now not merely still wrong — it is wrong in a new and much more confusing way, and the job reported success.

Airflow calls the correct parameter the logical date or data interval; every orchestrator has an equivalent. Use it in every query, every file path, and every API call. There are no exceptions worth making.

Analogy

A recipe that says "use whatever is in the fridge" produces a different meal every time it is followed. A recipe that lists its ingredients produces the same meal today, next week, or when someone else follows it.

The logical date is the ingredient list. CURRENT_DATE is the fridge.

Backfills

A backfill is rerunning a pipeline over a past date range — because you fixed a bug, added a column, or a source restated its data. It is one of the most common activities in the job, which is why the two rules above matter so much: a backfill is just idempotency and logical dates being exercised at volume.

Three practical points:

  • Control the concurrency. Backfilling a year of daily partitions all at once will either exhaust your warehouse or cost a startling amount. Most orchestrators let you cap parallel runs; use it.
  • Backfill into a separate location first when the change is risky, then swap. Rebuilding in place means a half-finished backfill is visible to users as half-wrong data.
  • Watch out for the downstream. Rebuilding a table often means everything derived from it is now stale. Know what depends on what before you start — this is what lineage is for.

Failures, retries and alerts

Failures are normal. Design for them rather than treating each as a surprise.

FailureRight response
Transient — network blip, brief API 503Automatic retry with exponential backoff. No human involved
Upstream late — source has not deliveredA sensor that waits, then alerts after a defined timeout. Do not silently process nothing
Data wrong — a test failedStop before publishing. A blocked pipeline is far cheaper than a published wrong number
Logic broken — the code raised an errorAlert a human. This is not retryable and retrying just delays the fix
Success is not the same as correctness

The most dangerous state in a data platform is a green dashboard. Every task succeeded, every run is a tick — and the source stopped sending rows four days ago, so your job has been faithfully processing an empty file each morning.

Task status tells you your code ran. It says nothing about whether the data is right. You need both, and the second one is the subject of Quality.

How to structure a DAG

A few conventions that consistently pay off:

  • One task, one responsibility. A task that extracts, transforms and loads cannot be retried partway, and its failure tells you nothing about which part broke.
  • Make tasks small enough to rerun cheaply but large enough that the DAG is readable. A 300-task DAG nobody can look at is its own kind of failure.
  • Prefer sensors to sleeping. "Wait until the file exists" is robust; "start at 03:00 and hope" is not.
  • Keep business logic out of the orchestrator. Airflow should decide when things run; SQL and code should decide what they do. Mixing the two makes the logic untestable outside the scheduler.
The exercise that teaches this page

Schedule a pipeline daily. Let it run for a week. Then delete the last five days of output and backfill them.

If your output afterwards is identical to what it was before, your pipeline is idempotent and correctly parameterised. If you get duplicate rows, or five copies of today's data, you have just found the bug this entire lesson exists to prevent — and you found it on your own laptop rather than in production.

Checklist

  • Plan a backfill of one month, naming the three things you would check before starting
