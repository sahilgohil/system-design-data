Why transformation exists at all

Raw data arrives shaped for the system that produced it, not for the question you want to ask. Timestamps are strings. Money is in three currencies. The same customer appears as ACME Corp, Acme Corporation and acme corp. in three systems. Someone's "order" table has one row per shipment, and someone else's has one row per basket.

Transformation is the work of turning that into something a person can query without a folklore of caveats. It is where most of the code in a data platform lives.

ETL and ELT: where the T goes

The classic acronym is ETL: Extract, Transform, Load. Take the data out, clean it in a separate engine, then load the clean result. This was the standard for decades, because warehouse compute was scarce and expensive and you did not want to waste it on cleaning.

Then warehouse compute became cheap and elastic, and the order flipped.

ELT won for four reasons, and it is worth being able to state them:

  • Raw data is preserved, so you can re-derive anything when logic changes or a bug is found.
  • Warehouse compute is elastic — you rent it for the minutes the transformation runs.
  • SQL is accessible to far more people than Scala or Java, so analysts can own transformations.
  • Logic lives in version control alongside tests, rather than inside a GUI tool nobody can diff.

ETL is still right in three situations: heavy unstructured work (parsing PDFs, images, logs) that SQL cannot do; personal data that must be masked before it lands anywhere; and transformations needing a library your warehouse cannot run.

The four words that explain distributed performance

When one machine is not enough — Spark, or a warehouse's internal engine — work is split across many. You do not need to know how the scheduler works, but four terms explain most performance problems you will meet, and knowing them turns "the job is slow" into an actual diagnosis.

TermWhat it isSymptom when it goes wrong
PartitionA chunk of data one task processesToo few: no parallelism, one core busy. Too many: scheduling overhead dominates
ShuffleMoving data across the network so related rows meet on one node. Required by joins, GROUP BY and sortsThe slow stage. Almost always the slow stage
SkewOne partition far larger than the rest199 tasks finish in seconds, one runs for an hour
SpillA task exceeds memory and writes to diskSudden order-of-magnitude slowdown; usually caused by skew
The classic skew story

A job that ran in 8 minutes now takes 90. Nothing changed in the code. The cause is almost always a join key where one value dominates: a NULL user_id, or a "guest checkout" account that holds 40% of all orders.

Every row with that key must land on one node, so one task does 40% of the work alone while the cluster idles. Adding machines does nothing — this is why "just make the cluster bigger" so often fails to help.

The tell: look at task durations in the UI. Even distribution means a genuine scale problem; one outlier means skew.

The SQL transformation layer

Modern practice is to express transformations as version-controlled SQL models with declared dependencies. dbt is the dominant tool here, with SQLMesh as a notable alternative.

The value is not the SQL — you could always write SQL. It is everything around it:

  • Dependency resolution. You write ref('stg_orders') instead of a table name, and the tool works out the build order.
  • Environments. The same code builds into a dev schema and a prod schema.
  • Tests. Uniqueness, not-null and referential assertions run as part of the build.
  • Documentation and lineage. Generated from the code, so it is accurate rather than aspirational.

If you learn one transformation tool, learn this category. It is the closest thing the field has to a default.

Stream processing, in the amount you need now

If you process unbounded streams — Flink, Spark Structured Streaming, Kafka Streams — three concepts carry the weight.

Windows

You cannot aggregate an infinite stream, so you group by time.

WindowShapeUse for
TumblingFixed, non-overlapping: 10:00–10:05, 10:05–10:10Regular reporting buckets
SlidingFixed length, overlapping: every minute, covering 5 minutesRolling averages, alerting thresholds
SessionBounded by inactivity gapsUser sessions, where the natural end is "they stopped"

State

The running data a job holds between events — counts so far, last value seen, an open session. State must be checkpointed to survive a restart, and it is the main source of operational pain in streaming. A batch job that dies has lost nothing; a stream job that dies has lost its memory of the world unless you arranged otherwise.

Watermarks

The engine's estimate of "we have probably now seen everything up to time T", which is what finally allows a window to close and emit a result. Anything arriving later is dropped or diverted, according to a policy you configure. This gets a full treatment in Reliability, because it is really a correctness topic wearing a performance costume.

Why streaming is harder, in one sentence

In batch, time is a column you filter on; in streaming, time is a property of the system itself — and the moment your correctness depends on the system's opinion of what time it is, everything gets harder.

Full refresh before incremental

Every transformation faces the same choice: rebuild the whole table, or process only what is new?

Start with full refresh. It is simple, it is self-correcting, and it exercises every line of your logic on every run. Move to incremental when runtime or cost actually demands it, not in anticipation.

The reason for that ordering is subtle and important: incremental logic is the code path that is not exercised on a normal run. Bugs there hide in the gap between "what a full rebuild would produce" and "what a series of incremental runs produced" — and that gap can grow silently for months. The patterns for doing it safely are in Modelling.

Try this

Take any transformation you have written and ask: if I ran a full rebuild right now, would the result match what is in the table? If you cannot answer confidently, you have found the most valuable test you could add.
