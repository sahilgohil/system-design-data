Assume every step fails halfway

A job writes 60% of its output and the machine dies. A network call succeeds but the acknowledgement is lost, so the sender retries something that already happened. A source restates last week's numbers without telling anyone.

None of these are edge cases. At any real volume they happen weekly. The question is not whether your pipeline will be interrupted mid-write — it will — but what state it leaves behind when it is.

The three delivery guarantees

The reasoning is worth walking through, because it explains why "exactly-once" is such a slippery marketing term.

A sender transmits a record and waits for an acknowledgement. The acknowledgement does not arrive. Two possibilities: the record never landed, or it landed and the acknowledgement was lost. The sender cannot tell these apart. It must either retry — risking a duplicate — or not — risking loss. There is no third option available at the transport layer, however sophisticated.

So real systems choose at-least-once and accept duplicates. You then make the duplicates harmless by ensuring that writing the same record twice has the same effect as writing it once. That is idempotency, and it is why practitioners often say "effectively-once" instead.

"Exactly-once" on a product page

When a tool advertises exactly-once, it almost always means exactly-once within its own boundaries — its internal state and its own sink, using transactions it controls end to end.

The moment your pipeline writes to something that tool does not control — an external API, a table another job also writes to, a file in a bucket — the guarantee ends at that boundary. It is a real feature; it is just narrower than the name suggests. Read it as "we handle our part", and handle yours.

Three ways to make a write idempotent

In rough order of preference.

1. Overwrite by partition

Replace the entire logical partition you are processing, rather than adding to it.

DELETE FROM daily_sales WHERE dt = '2026-03-01';
INSERT INTO daily_sales SELECT ... WHERE dt = '2026-03-01';

Simple, robust, and requires no unique key at all. It is a large part of why date partitioning is so universal — partitioning is not only a performance decision, it is a correctness one.

2. Merge on a stable key

MERGE INTO orders t USING staged s ON t.order_id = s.order_id
WHEN MATCHED THEN UPDATE SET ...
WHEN NOT MATCHED THEN INSERT ...;

Handles updates as well as duplicates, which overwrite-by-partition does not when a record moves between partitions. It requires a genuine business key — order_id, not a row number.

3. Deduplicate on read or in staging

SELECT * FROM (
  SELECT *, ROW_NUMBER() OVER (
    PARTITION BY event_id ORDER BY ingested_at DESC) AS rn
  FROM raw_events
) WHERE rn = 1

Keeps every copy and picks a winner. Useful when raw must stay append-only, at the cost of doing the work on every read.

Ask for a unique key on day one

All three techniques depend on being able to identify the same record twice. Ask every source for a stable unique identifier at the start of the project — retrofitting one is painful and sometimes impossible.

If a source genuinely has none, synthesise a deterministic hash of the fields that define uniqueness. Never a random UUID generated at ingestion time: it differs on every rerun, which defeats the entire purpose while looking like it solved the problem.

Late and out-of-order data

Two clocks exist, and conflating them produces numbers that are wrong in ways nobody notices.

  • Event time — when the thing actually happened.
  • Processing time — when your system saw it.

This is not an exotic scenario. Mobile apps buffer events offline. Vendors restate attribution data for three days. Payment providers attach refunds to charges from weeks ago. Any system with humans or devices at the edge has late data, always.

Handling it in batch: the lookback window

Do not reprocess only yesterday. Reprocess the last N days on every run, where N comes from the observed lateness distribution rather than a guess.

Measure it: for a sample of records, compute ingested_at - event_time and look at the p99 and p99.9. If 99.9% of events arrive within four days, a seven-day lookback covers you with margin. Costs a little compute every night; prevents a class of silently wrong numbers.

This is only safe if the write is idempotent — reprocessing seven days with an INSERT would give you seven copies. The two ideas on this page depend on each other, which is why they share a lesson.

Handling it in streaming: watermarks

A watermark is the engine's assertion that everything up to time T has probably arrived, which lets a window close and emit a result. Anything later is dropped, or routed to a side output for separate handling.

The allowed lateness is a configuration value, and it is genuinely a business decision, not a technical default. "We will count events up to 2 hours late and discard the rest" is a statement about what the numbers mean, and someone other than you should agree to it.

Store both timestamps. Always.

Every record should carry event_time (when it happened) and ingested_at (when you received it). It costs two columns.

Aggregate on event time, monitor freshness on ingestion time, and measure lateness by subtracting one from the other. Without both, "why is last Tuesday's number different now?" is unanswerable.

Restatement: deciding what history means

If you reprocess late data, historical numbers change. Someone will notice, and the conversation is much better if you had it in advance.

PolicyMeansSuits
Always currentNumbers update whenever new data arrives, silentlyProduct analytics, experimentation
Announced restatementHistory can change, but a change is communicatedMarketing attribution, operational reporting
Frozen after a periodAfter close of month, the number never moves againFinance, regulatory reporting

Finance teams care about this intensely. Discovering their expectations after you have silently changed last quarter's revenue is a genuinely bad day, and one that damages trust in the platform for a long time afterwards.

The exercise

Run a streaming consumer that writes to a table. Kill it mid-run. Restart it. Count the rows.

Then add an event_id and a deduplicating read, and do it again. The difference between the two row counts is the whole of this lesson, and seeing it on your own machine makes it permanent in a way reading cannot.

  • Make a non-idempotent write idempotent, choosing correctly between overwrite, merge and dedup for a given situation
  • Say why a random UUID assigned at ingestion is a broken deduplication key
  • Distinguish event time from processing time, and give a real scenario where the gap is days
  • Choose a lookback window from a lateness distribution rather than by intuition
  • Name the three restatement policies and say which one a finance team will want
